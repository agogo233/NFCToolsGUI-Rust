**apply() 契约（S1 实现要点）**

- 只消费「工具/任务运行期推送」类事件；`Guidance`、`BinaryData`、`DictFileName`、`HardNestedConfig`、`DictTestConfig` 属 UI 主动发起或纯渲染，`apply` 直接忽略。
- `TaskDone` 对标 `execUtils.js::exec` 的 `close` 回调：先清 `is_running_task`，随后仅 `code != 0` 才走失败路径（被 kill → 事件条 error + `printExitLog(2)` 复位空闲；非零退出 → 日志 `exit code: N` + 事件条 error + `printExitLog(1)` 置出错）。**`code == 0` 时 core 不做收尾**，由 S5 任务模块推送 `Status`——与原版 command.js 里 `.then(() => printExitLog(0))` 一致。
- `Log` 对标 renderer 的 `onUpdateLogOutput`：块内含 `\33[2K` 时先把 `log_buffer` 截断回最后一个 `\n`（无 `\n` 则整体清空，即 JS `substring(0, -1) === substring(0, 0)`），再剥离该序列后追加。逻辑落在 `append_log`，runner 只做透传。
- `EventKind` 三色：`Key` / `Error` / `Success`。原版 `success` 由 renderer 在 `onDumpSaved` 本地产生，此处收拢进 core，故 `DumpSaved` 同时写 `dump_history`（按文件名去重）并追加一条 `Success` 事件。

## 5. 线程模型与执行框架

原版是 push 模型（Node `spawn` 的 data/close 事件直接回调 UI）。这里改成 **pull 模型**：
UI 线程每帧主动 `pump` 一次，拿到输出块就喂 `AppState::apply`。既不阻塞 egui 渲染循环，
也天然满足单任务锁——`start` 被门禁拒绝时根本不会产生输出。

```
UI 线程（egui）：
    渲染 + 分发 action + 每帧 runner.pump(...) → AppState::apply
    同一帧内 runner.exit() 取退出码 → AppState::apply(TaskDone)
    │ 500ms 定时 serial.list() 热插拔比对
worker 线程（std::thread，每工具 3 条，零 tokio）：
    ├─ stdout 线程：read 4096 → mpsc<Chunk>
    ├─ stderr 线程：read 4096 → mpsc<Chunk>
    └─ 协调线程：join 前两者 → 置位 ready
退出码由 UI 线程在 exit() 里用 Child::try_wait() 轮询取得，不落后台线程。
```

### pull 模型的调用契约

UI 每帧按 `pump` → `exit` 的顺序调用：

- `pump` 排空该帧输出块并从 `pending` 计数器减一。
- `exit` 只在「`pending == 0` 且两个 reader 线程都已结束」时才返回退出码。

两个 `ToolRunner` 实现共享这条契约（真实现靠 `pending` 计数 + `ready` 标志，Mock 靠
`drained` 标志）。**不可先 `exit` 再 `pump`**：尾部块会随 `Receiver` 析构一起丢失。

`ready` 必须是可重复读取的标志位而非一次性 channel：`exit` 先判 `ready` 再 `try_wait`，
若 `try_wait` 返回 `Ok(None)`（子进程先关了管道但尚未退出），信号不能因此被消费掉，
否则下一帧再也判不到「reader 已结束」，`exit` 永久 `None`、`is_running_task` 永不清零。

`kill` 与 `exit` 共用同一把 `Mutex`，但锁的持有时间只够一次 `try_wait`（微秒级），
故 `kill` 的加锁不会卡住 UI 线程。切勿改成在持锁状态下调用 `Child::wait()`：
wait 会阻塞到进程退出，而唯一能终止进程的 `kill` 恰好被这把锁挡住，直接死锁。

### runner.rs 门禁与错误

```rust
pub const ALWAYS_ALLOWED: &str = "nfc-list";

#[derive(thiserror::Error, Debug, Clone, PartialEq, Eq)]
pub enum ToolError {
    #[error("device not connected")] NotConnected,
    #[error("task already running")] Busy,
    #[error("task killed")] Killed,
    #[error("tool exited with code {0}")] Failed(i32),
    #[error("failed to start tool: {0}")] SpawnFailed(String),
}

#[derive(Debug, Clone, Copy)]
pub struct GateState {
    pub has_current_device: bool,   // status.currentDevice !== null
    pub is_device_connected: bool,  // status.isDeviceConnected
    pub is_running_task: bool,      // status.isRunningTask
}

pub fn gate(tool: &str, st: GateState) -> Result<(), ToolError>;

#[derive(Debug, Clone, Copy)]
pub struct Exit { pub code: Option<i32>, pub signal: bool }
impl Exit { pub fn result(&self) -> Result<(), ToolError>; }
```

**spawn 前置**（对标 execUtils.js::exec 的两个 `if`，判定顺序一致）：
`currentDevice === null` 一律 NotConnected；否则 `!isDeviceConnected && cmd != ALWAYS_ALLOWED`
→ NotConnected；再 `isRunningTask → Busy`。**该检查不受 `ALWAYS_ALLOWED` 豁免**。
两道门禁之外 `start` 还会看 `self.job.is_some()` 兜底返回 Busy，防止调用方绕开门禁直接启动，
对应原版的「单任务」语义。

**退出码**：`code == Some(0)` → Ok；`signal` → Killed；否则 `Failed(code)`。

### 与原版 exec 的偏离

| 项 | 原版 | 本实现 | 影响 |
|---|---|---|---|
| 输出粒度 | data 块由 libuv 决定尺寸（流缓冲 64KB），原样交 processHandler | 同样按块（`read` 4096 字节），不拆行 | 同为块粒度，块更小；判定子串恰好跨块时被截断的概率略高于 Node。原版 command.js 全用 `value.indexOf(...)` 比对单块，风险同源，非 Rust 新增 |
| 终止信号 | `task.kill()` → SIGTERM | `Child::kill()` → SIGKILL（std 无按信号杀的能力） | 工具收不到 SIGTERM 清理机会；退出仍走 signal 分支 |
| signal 判定 | `close(code, signal)` 两个参数都有 | 用 `code.is_none()` 推断 `signal` | Unix 上等价。偏离：Windows 无信号语义、`code` 恒为 `Some`，被信号终止的进程会误报 `Failed`（原版 JS 在 Windows 上同样无 `signal`，行为同源）。`try_wait()` 返回 `Err`（`ECHILD`/`ECHECK`）时按「尚未结束」继续轮询，不会误报为 signal |
| 门禁拒绝副作用 | 拒绝时顺带 `printStatus(i18n("indicator_error"), "error")` 置状态条出错 | `gate()` 是纯函数，只返回 `Err(NotConnected)`，不发 `Event::Status` | 调用方须自行补一条 `Status` 事件，否则状态条会与原版不同 |
| 超时 | 原版 exec **没有**超时逻辑 | 未实现 | 一致（原稿曾列 `Timeout` 变体，已删） |

`TaskDone { code, killed }` 中 `killed` 即 `Exit.signal`；`code` 为 `None` 时按原版语义交给
调用方处理（非 0 路径），S5 收尾用。

## 6. 与原版行为的偏离登记

原版（Electron/AGPL）有若干处缺陷与不可取证项。本项目逐条登记，**只修会造成功能失效、
数据损坏或静默错误的部分**；纯外观差异也一并登记，便于后续复核。

> 编号沿用审计清单的 `#N`，**故意跳号**（缺 #5/#8/#9/#10/#11/#13）：那些缺陷属 S5/S6
> 范围（写卡成功提示、字典路径取首字符、i18n key 拼写、扩展名过滤、stdout/stderr 汇流、
> ETA 分母估算），本步未触碰，届时另行登记。

- **时间戳为 UTC（偏离原版）**：原版 JS 用 `new Date()` 按本地时区生成 `yyyy_MM_dd_HH_mm_ss`；Rust 侧 `SystemTime` 无时区信息，当前实现输出 **UTC**。Windows 用户（UTC+8）看到的 dump / 日志文件名会比原版早 8 小时。S12 引入时区库（`chrono-tz`）后补齐。

### 8.1 build.rs（位于 `crates/nfc-app/build.rs`，替代 buildInfo.json）

```rust
fn main() {
    let hash = std::process::Command::new("git")
        .args(["rev-parse", "--short", "HEAD"])
        .output().map(|o| String::from_utf8_lossy(&o.stdout).trim().to_string())
        .unwrap_or_default();
    println!("cargo:rustc-env=GIT_HASH={hash}");
    println!("cargo:rustc-env=APP_VERSION=v1.0.0");
    let builder = std::env::var("NFCTOOLSGUI_COMPILER")
        .unwrap_or_else(|_| std::env::var("USERNAME").unwrap_or_else(|_| "local".into()));
    println!("cargo:rustc-env=BUILDER={builder}");
    println!("cargo:rerun-if-changed=../../.git/HEAD");
}
```

> 说明：build.rs 必须位于含 `[package]` 的 crate（nfc-app），workspace 根是纯 `[workspace]` 不生效。
> Windows 下用户名取 `USERNAME`（`whoami` 非标准、不存在于 rust std）。
> `rerun-if-changed` 的路径相对于**包根**（`crates/nfc-app/`），故 `.git/HEAD` 需写成 `../../.git/HEAD` 才能上溯到仓库根；写成 `.git/HEAD` 会指向不存在的 `crates/nfc-app/.git/HEAD`，导致 GIT_HASH 永不刷新。

返回值，导致点「取消 / 确定」面板不关。已由 `c_panel_closes_on_cancel` 锁定。

### 6.9 S10 dump 三面板的偏离与安全加固

**偏离**

| 项 | 原版 | 本项目 | 理由 |
|---|---|---|---|
| `dumpfiles/` 列表排序 | `readdirSync` 的返回顺序由文件系统决定（多数实现是目录项顺序，非字典序），UI 每次刷新顺序可能跳变 | `dumpfiles::list` 显式按文件名升序 | 确定性优先。纯 UI 表现层。 |
| 比较器 diff 的分段 | 相同字符也是逐个原样拼接，不合并成段 | 连续的相同字符合并成一个 `Same` 段 | 纯内部优化。**差异粒度仍是字符**（每个不同字符各一个 `Diff` 段，对齐原版每个不同字符各一个 `<mark>`），渲染结果逐字一致。见 `dump::diff_line` 的测试。 |
| 比较器扇区行数不足 | 内层循环固定 4 轮，`dumpA[i][3]` 为 `undefined` 时该行被当"无差异"输出，渲染出字面量 `undefined` | 按 `min(4, 实际行数)` 走并补空行 | 不复刻该 bug。合法 dump 恒 4 行，两者结果一致。 |
| 编辑器读文件失败 | `if (err) throw err` 整个窗口崩掉 | 记成一条 error 事件，UI 继续可用 | 见 `NfcApp::load_dump_into_editor`。 |

**安全加固（非偏离，是原版的漏洞）**

原版 `delete-dump` / `rename-dump-file` 直接 `path.join(dumpsFolder, file)`。
Node 的 `path.join` 遇到**绝对路径**的第二段时会丢弃前半段，即
`path.join("/a/dumpfiles", "/etc/passwd")` → `/etc/passwd`。
配合 UI 里文件名可被重命名改成任意内容，等于可以删/改 dump 目录外的任意文件。

本实现在 `dumpfiles` 模块统一做白名单校验（`is_plain_name`）：
非空、非 `.` / `..`、不含 `/` `\` `\0`。见 `c_dumpfiles_reject_traversal`。

**保存按钮的两道检查**

原版 `dumpEditor.js:16` 是 `if (!currentFilePath || !getHexData()) { alert }`
**加** `:20` 的 `checkData(true)`，两道都要过。`dump::validate` 对空扇区列表
返回 `Ok`（原版 `.each` 遍历空集合的 vacuous truth），所以真正的把关在
`EditorForm::can_save()`：`file_name.is_some() && !sectors.is_empty() && validate(true).is_ok()`。
缺了 `!sectors.is_empty()` 那一项就会写出 0 字节文件（`Buffer.from("")`）。

### 6.10 S11 接线层的两处判断

**`nfc-list` 不占任务位**

`Engine::is_running()` 只看 Engine 自己的 `running` 字段，**不**并上
`runner.is_running()`。若并上，会出现自锁：`scan-usb-devices` 拉起 `nfc-list`
→ `runner.is_running()` 为真 → 用户随即选设备触发 `conn-usb-devices`
→ 门禁的 `is_running_task` 读到真值而拒绝自己刚发起的连接。
原版 `execUtils.js` 的 `nfc-list` 例外正是这个意思：它不是一个"任务"。

**`currentDevice` 为 null 时连 `nfc-list` 也被门禁拒**

`runner::gate` 的第一道是 `!st.has_current_device`，**先于**
`tool != ALWAYS_ALLOWED` 的豁免生效。故未选设备时 `nfc-list` 也跑不了。
这不是 bug，是原版行为——S3 定 `GateState` 时就已对拍并写进注释
（`status.currentDevice !== null` 为 null 时无条件拒绝，含 nfc-list）。
写 S11 测试时我一度以为 `ALWAYS_ALLOWED` 能豁免这条，被测试打脸后确认了原意。

**未接线动作必须显式报错**

`ToolError::NotWired(&'static str)` 是 S11 新增的变体。S8–S10 里
所有未接线的动作都走 `Action::Plain` 进队列再被 `clear()` 丢掉，
表现为"点了没反应"——用户无从判断是门禁拦的、工具崩的，还是根本没实现。
现在未识别的 action 会记一条 error 事件 + 一行日志。

### 6.11 S11-2 系统文件对话框的四项取舍

**① 危险确认框改为应用内模态窗（刻意偏离）**

原版的删除 / 写卡 / 锁卡确认用 `dialog.showMessageBoxSync`
（`command.js:507` / `:112` / `:222`），是**同步阻塞**调用。而我们的
`DialogProvider` 是同步 trait，由 `Engine::dispatch` 在自己的调用栈上取值。
在 eframe 的 UI 线程上弹同步原生框，会让主窗口在用户点「确定」之前
完全无法重绘——而这个框恰恰出现在最需要看清当前状态的时刻（写卡前）。

改法：确认框在 app 层自绘（`dialogs_ui.rs`）。流程随之两段化：
app 收集用户意愿 → 预置进 `ScriptedDialog::confirm_results` → 派发动作
→ engine 侧 `prepare_write` 等照常调 `confirm_danger`，拿到的是预置值。

代价：外观与原版的系统消息框不同。

**② 文件框走「专用线程 + 通道」**

rfd 的 `pick_file()` / `save_file()` 是阻塞调用。`dialogs_host.rs` 起一个
`nfc-dialog` 工作线程，界面线程只做「投递请求」与「每帧收取结果」，
系统弹窗打开期间界面照常刷新（底栏显示「正在等待选择文件…」）。
退出时**故意不 join** 工作线程——弹窗可能还开着，join 会卡住主线程。

选择「预选路径 + 引擎不弹框」而非「把 `DialogProvider` 改成异步」，
是因为 `prepare_write(paths, dump_id, dialog)` / `prepare_write_uid(..., dump_path)`
本来就接受预先给好的路径。core 因此**一行未改**，测试仍可完整驱动。

**③ 弹窗无父窗口（无法规避的限制）**

eframe 0.36 的 `CreationContext` 其实**实现了** `HasWindowHandle` /
`HasDisplayHandle`（`eframe-0.36.2/src/epi.rs:100-107`），而 rfd 的
`set_parent<W: HasWindowHandle + HasDisplayHandle>` 正是这个签名——
所以**类型上并非不可用**，先前那句「公开 API 取不到」是错的。
真正的障碍是两个：① `CreationContext` 只活过 `run_native` 的创建闭包，
存不进 `NfcApp`；② 工作线程在该闭包之外运行，拿不到它。
另：XDG portal 后端本就忽略 parent。
功能正常，但弹窗不是模态于主窗，极端情况下可能出现在窗口后面。

**④ rfd 不区分「用户取消」与「后端不可用」**

rfd 0.17 的阻塞 API 返回 `Option<PathBuf>`，两者都是 `None`。Linux 上
没有桌面门户服务时，表现为「点了没反应」。这是 rfd 的 API 形状决定的，
不是我们能修的。

缓解：`dialogs_host::file_dialogs_supported()` 在启动时探测会话总线，
无头 / SSH 环境下给出一条明确的错误事件与日志。探测是启发式的
（`portal_available` 为纯函数，四种组合均有单测），**不能覆盖全部失败原因**。
另：Linux 用默认特性（`xdg-portal` + `wayland`），`gtk3` 是可选且非默认，
故不引入任何 GTK 系统依赖；Windows 走原生弹窗，同样零系统依赖。

### 6.12 S11-2 修掉的真缺陷

这些不是「刻意偏离原版」，是本重写自身的 bug，故单列。分两批：
第一批是实现时发现的，第二批是独立代码审计后发现的。

#### 第一批（实现时）



这些不是「刻意偏离原版」，是本重写自身的 bug，故单列。

**① `format-card` 缺了备份前置**

S11 第一步把 `format-card` 实现成「读 temp 的厂商块后直接启动格式化」。
但原版走的是 `readICThenExec`（`command.js:145-148`）——**先读卡备份，
再格式化**。更关键的是 `command.js:603-607` 的安全闸：备份文件没生成
就**中止，绝不格式化**。缺少这道闸意味着「卡读不出来时照样把卡格式化」。

现已补上两段式编排（`Engine::read_then_exec` + `start_next_stage`），
备份缺失或大小为 0 一律中止并记「读卡失败，未执行操作」。
`write-IC` 同样受益（原版走同一个 `readICThenExec`）。

**② 成功退出后指示灯卡在「运行中」**

`printExitLog(0)`（`execUtils.js:75-78`）对**所有**工具一视同仁地置空闲。
而 S11 第一步只在 `run.name` 是 `read-IC` / `done-input-keys-read-IC` 时才复位，
于是 `detect-card-type` / `dict-test` 跑完后状态灯一直停在运行中。
现已改为任何成功退出都落回空闲，并补 `log_msg_finished` 日志。

**③ 面板绕过危险确认**

历史面板的「写这张卡」直接 `push(Action::WithArg("write-IC", ..))`，
「删除」直接 `push(Action::DeleteDumps(..))`，两者都跳过了确认。
现已改走 `NfcApp::exec` → 应用内确认窗。engine 侧另加一道
`confirm_danger` 闸，即便绕过 UI 直接派发也删不掉东西。

**④ 比较器从历史打开时两侧是空的**

`Action::OpenComparator` 只被 engine 收下即止，从没把 A/B 读进表单——
点「比对」打开的是一个空比较器。现按原版 `command.js:460-467` 的
`{A, B}` 载荷载入两侧。

**另修两处定位/接线缺口**

- `framework_bin()` 的文档承诺「打包 = exe 旁、开发 = 仓库根」，实现却只是
  简单 `join`，开发时实际指向 `target/debug/framework/bin`。已改为向上逐级查找。
- `rename-dump-file` 是 30 个 action 里唯一**完全没有 UI 入口**的。
  已按 `dumpHistory.js:29-53` 补行内重命名（失焦或回车提交，另加 ✓ 按钮）。

#### 第二批（独立代码审计后，全部带回归测试）

**① 备份段非 0 退出仍会执行写卡**（破坏性路径，最严重）

原版 `exec` 在 `code !== 0` 时 **reject**（`execUtils.js:51-52`），而第二段
挂在 `.then()` 上（`command.js:600`）——reject 后 `.then()` 不执行，
即备份失败**绝不**继续写卡。首版实现只检查「`temp.mfd` 是否生成」，
忽略了退出码：读卡器中途异常但已写入部分数据时，会继续把卡格式化掉。
已把 `run.next` 的处理移进 `exit.result()` 的 `Ok` 分支。

**② 批准按队列位置绑定，热插拔会抢批**

批准原先单独存在 `approved: Vec<bool>`，派发时按位置取。而热插拔每 500ms
往 `pending` 里塞一个 `ScanUsb`，若恰好同帧，批准会被 `ScanUsb` 先消费掉
→ 用户在「锁死 UFUID / 写卡 / 删除」上点了确定，却**什么都没发生**且无提示。
已改为批准与动作成对入队（`pending_with_approval: VecDeque<(Action, bool)>`）。

**③ 重命名的回车提交是死代码**

原写成 `r.lost_focus() && ui.input(|i| i.key_pressed(Enter))`，两个条件互斥
（单行 `TextEdit` 按回车不失焦，失焦那帧通常也没有回车），回车提交永不触发。
已改为 `||`，与原版「失焦**或**回车」一致。

**④ 写 UFUID 的确认框不显示 block0**

原版 `command.js:210-214` 把 block0 hex 显示给用户看再确认。engine 侧的
`prepare_write_uid` 虽也拼 hex 进 `confirm_danger`，但那次确认框不再呈现
（已改成 app 层自绘），于是用户实际**看不到**将写入哪个 0 块。
已让 app 层在 `on_file_reply` 里自己读一次 block0 并拼进确认正文。
（此修复顺带暴露一个二次 bug：`ConfirmKind::WriteUid` 的载荷一度被写成
basename，而 engine 需要完整路径，已一并修正并加断言。）

**⑤ 五个面板按钮绕过 `exec`**

字典面板「选择文件」直接 `push(Plain("open-dict-file"))` → engine 纯 UI
no-op → **毫无反应**；编辑器「打开文件」、比较器 A/B 直接 push 未注册的名字
→ 弹 `NotWired` 错误；编辑器「保存 / 另存为」push `Action::SaveDump`
→ engine no-op → **保存完全不生效**。首版只接了 `exec` 的字符串路径，
真实 UI 入口一个都没接。已全部改走 `exec`，比较器补上 `"A"` / `"B"` 载荷。

**⑥ `dump-editor-save` 过滤器与默认路径都错**

原版另存为的过滤器是 `mfd` / `dump`（`command.js:444`），却用了 `save-log`
的 `txt`；`default_path` 传的是裸文件名而契约要求完整路径，
导致保存框停在进程 CWD。均已修正。

**⑦ `save-log` 默认路径凭空加了目录**

原版 `command.js:541` 的 `defaultPath` 是**裸文件名**（无 `path.join`），
首版却拼上了 `dumpfiles/`，且把该错误写进了注释。已按原版改为裸名。

**⑧ 读卡收尾从未落盘（主流程断掉）**

`mfoc::dump_save` 实现完整却**没有任何生产调用者**，于是 `read-IC` 成功后
既不保存 dump、也不发 `Event::DumpSaved`，引导条永不出现——
「读卡 → 写这张卡」这条核心流程根本走不通。已在 `Engine::finish` 的
`read-IC` / `done-input-keys-read-IC` 分支接入，并补上从 mfoc 输出抓
`UID (NFCID1):` 作为默认文件名前缀（`command.js:641-645`）。
`Engine::pump` / `finish` 因此新增 `dialog` 参数（`dump_save` 需要询问落盘路径）。

**⑨ `hard-nested` 成功退出后误置「空闲」**

原版 `hard-nested-config-done` 的 autoRun 分支走 `readICThenExec` 的 4 参
形式，其 `.then()` 只做 `printStatus(statusMsg); cmd(); return;`，
**不调 `printExitLog(0)`**——状态要留给紧接着的 `run-hard-nested`。
已加 `chain_continues` 标记，链路型工具不置空闲。

**⑩ 静态核验脚本不在仓库里**

docs 声称 parity 表「由静态脚本守住」，但脚本在 `/tmp` 下，
克隆仓库的人拿不到，保护实际不存在。已移入 `tools/verify_parity.py`，
路径改为相对脚本解析，原版源码缺失时相关项自动跳过而不崩。

### 6.13 S12 交付层的刻意偏离

**`framework/bin` 缺失引导**

`framework/bin` 是 gitignore 的（8 个 C 工具需原版项目的 `compile.sh` 生成）。
自检按 `runner::KNOWN_TOOLS` 逐个探测，并**同时试带 `.exe` 的形式**——
`Path::is_file()` 是纯文件系统检查、不补扩展名（Windows 上 `CreateProcess`
才会自动补），只查裸名会让红条永远显示。
原版没有启动自检：缺失时只有用户点下某个按钮，才在 `child_process.spawn`
处抛一条 IO 错误（`ENOENT` + 一长串路径），用户无从判断是驱动没装、
路径不对，还是根本没编译。

本实现在启动时探测（`runner::missing_tools`），缺失则：
- 顶部显示红色引导条，列出缺哪些工具与期望的目录路径
- 事件条与日志各记一条，指向「在原版目录跑 compile.sh」

**上溯查找设 5 层上限**

`runner::framework_bin` 为支持「开发时 = 仓库根」会向上逐级查找。
无界上溯有风险：从 `target/debug` 一路走到 `/`，中途任何一层若恰好有
`framework/bin`（用户在别处解开的源码包），就会被误命中并 spawn 其中
来历不明的同名程序。故设 `MAX_LOOKUP_LEVELS = 5`。

**release profile**

`panic = "abort"` + `strip = true` + `lto = "thin"`。
GUI 场景下 panic 栈回溯没有消费者，`abort` 省下 unwind 表；
`strip` 去掉符号表与调试段。实测 `nfc-app` release 产物 **17.7MB**
（Linux x86_64，未含 `framework/bin`）。原版 Electron 打包后 100MB+。

### 6.14 S11-6 审计发现的「数据流没接上」类缺陷

§6.12 记的是「接线漏了」，这一节记的是更隐蔽的一类：**骨架接上了，
但数据没往下游流**。绿灯全绿、静态守卫全过，功能却是不通的。

**① `known_key_info` / `unknown_key_info` 从未在生产代码里写入**

`tasks::detect::after_detect` 此前只把新密钥**落盘**，不回填这两个列表。
于是：

- `detect-card-type` 跑完 `unknown_key_info` 恒空 → 未知密钥引导永不出现
- hard-nested 面板永远显示「无检测结果」，全部输入禁用
- HardNested autoRun 每轮都走 `StopNoKnownKey`（「未发现已知密钥」）

即「检测 → 破解」这条核心链路是断的。修法：把解析结果回填进 `AppState`，
放在 temp 校验**之前**——校验失败也要保留已解析出的信息，否则用户会丢掉
刚探测到的密钥列表。

**② autoRun 的「无进展」判据恒真，多轮闭环只跑 1 轮**

`Engine::finish` 里 `after_crack_guarded(cfg, unknown_before, unknown_after)`
的第三参误用了 pop **之前**的快照长度。它与 `unknown_before` 恒相等
（两次快照之间没有 mfdetect），于是 `unknown_after >= unknown_before`
永远成立，autoRun 每轮都在第 1 轮后打印「本轮未解出任何密钥」并停住。

这个缺陷**单轮测试抓不到**——单轮里 `unknown_before` 与 pop 前后长度恰好
不同。必须写一个跑满多轮的用例。为此给 `MockToolRunner` 加了
`with_scripts`（逐次喂不同脚本）：此前每次 `start` 都完整回放同一份
script，第 1 轮与第 2 轮无从区分，结构上就写不出多轮测试。

**③ collectOnly 采到的 nonce 被静默丢弃**

`Step::SaveNonces` 直接置空闲——没有非空判定、没有保存框、没有 `rename`。
`hard_nested::nonces_default_name` / `nonces_is_empty` / `clear_nonces`
三个函数都写好了却无人调用。已按 `command.js:310-332` 接上
（含 autoRun 起手清空 `nonces.bin`，`command.js:249`）。

**④ HardNested 的状态条进度被 `launch` 覆盖**

先 `apply(Event::Status{进度文案})` 再 `launch(...)`，而 `launch` 内部会再
apply 一次静态 i18n 文案把它盖掉。原版 `exec()` 根本不调 `printStatus`，
状态条停在带 `已解/总数` 的文案上。已拆出 `launch_with_status`。
同时 `hn_progress_text` 补上 `auto_run` 判据：原版采集处的进度后缀
**只有 autoRun 才带**（`command.js:284`），破解处才无条件带。

**⑤ `missing_tools` 在 Windows 上恒报缺失**

`tool_path` 不带扩展名（对齐原版 `binPath + cmd`），而 `is_file()` 不补
`.exe`。Windows 是主目标平台，红条会永远显示。见 §6.13。

### 6.15 一条如实保留的原版缺陷

`tasks::mfoc::take_uid` 的 14 字符窗口按**含空白**计、之后才去空白
（对齐 `command.js:641-645` 的 `substring(i, i+14)` + `replace(/\s+/g,"")`）。
故 mfoc 若把 UID 折行且缩进较深，取到的 ID 会被截断。刻意不改以维持
对拍一致——文件名前缀只是给用户看的默认名，截断不影响功能。

### 6.16 S11-7：「parity 表说完成，其实从没弹过框」

S11-6 修完数据流后，我核了一遍 30 个 action 的**实际接线**，发现 read-IC
收尾与 HardNested `collectOnly` 这两处保存框是**假的**：

`DialogProvider` 是**同步** trait（对标 Electron 的 `showSaveDialogSync`），
在 `Engine::pump` 里、**UI 线程上**被调用。生产实现是 app 侧的 `ScriptedDialog`，
它的 `save_results` 永远是空的 → `show_save_dialog` 恒返回 `None`
→ 落盘时静默用默认名。

即：**这两个框一次都没弹过**。parity 表上写着「已接线」，实际没有。
S11-2 的「app 预选路径」方案对它们根本不适用——预选要求「动作发起时就能问」，
而这两处的默认文件名含**流程中途才知道**的东西：

| 场景 | 默认文件名含 | 何时才知道 |
|---|---|---|
| read-IC 收尾 | 刚读出的 UID | mfoc 跑完 |
| collectOnly | 本轮 sector | libnfc-collect 跑完 |

**做法：挂起 + 续接。** engine 不弹框，改为记下
`pending_save`（含 `default_path` / `request` / `source`）并立刻返回控制权；
app 在帧循环里取走它、用已有的 `DialogHost` 弹 rfd，拿到路径后回调
`Engine::resolve_save` 落盘。core 全程不碰 GUI。

顺带清掉了一路-sync-参数：`finish` / `hn_start` / `hn_advance` / `hard_nested`
都不再需要 `&mut dyn DialogProvider`，`pump` 也一样。只有 `dispatch` 还留着
（`DeleteDumps` 的 `confirm_danger` 仍走同步 trait）。

**两处取消语义不同，别混：**

- read-IC 收尾取消 → **仍用默认名存**（`command.js:667` 的 `url || defaultName`）
- collectOnly 取消 → **保留 `nonces.bin`**（`command.js:310-320`），
  否则用户白采一轮

**一个真实的数据安全坑：** `finish` 开头已把 `is_running_task` 置 `false`，
而 Busy 门禁只看这个字段。若不重新置真，挂起期间能再发起一个 read-IC，
它会覆盖同一个 `temp.mfd`——用户在保存框里选好的路径就指到另一张卡的数据上。
现在 `finish` 挂起后会重新置真，`resolve_save` 再释放。

**另一处**：`pump_pending_save` 每帧都调，若不判 `dialogs_host.is_pending()`
就会重复投递——手动宿主下 outstanding 会一路涨到 6，真实环境里就是连弹 6 个
系统框。两条都有回归测试。

### 6.17 S12-2b：单测全绿，但主流程在二进制层面根本跑不起来

S12-2 首次把 C 工具真编出来（`framework/bin` 9 个），并把 engine 真正会
spawn 的每条命令行喂给真二进制。立刻抓到一个**发布级缺陷**：

**`read-IC` spawn 的是错的二进制。**

| | 原版 | 本重写（错） |
|---|---|---|
| 读卡 | `mfoc -O<dump> -f<keys>`（`command.js:104`/`:159`） | `nfc-mfclassic -O<dump> -f<keys>` |
| 写卡/格式化 | `nfc-mfclassic w A u <src> <temp> f`（`:119`/`:147`） | 同左 ✓ |

两个二进制**参数风格完全不同**：

- `mfoc` —— 开关式，`-O<dump> -f<keys>`
- `nfc-mfclassic` —— 位置参数式，`f|r|R|w|W a|b u|U<uid> <dump> [keys] [f]`

拿位置参数的二进制去吃 `-O/-f`，它会直接打 usage 退出。实测：

```
$ nfc-mfclassic -O/tmp/x/temp.mfd -f/tmp/x/keys.txt
Usage: nfc-mfclassic f|r|R|w|W a|b u|U<01ab23cd> <dump.mfd> ...
$ echo $?
1

$ mfoc -O/tmp/x/temp.mfd -f/tmp/x/keys.txt
The custom key 0xFFFFFFFFFFFF has been added to the default keys
No NFC device found.（实测粘贴，勿臆造）
```

后者才是「参数被接受、只是没卡」。

> 上面两段输出是**实测粘贴**（2026-09 于本机 `framework/bin`），
> 非臆造的判定串。

**为什么 453 个测试 + 610 项静态门禁全都没抓到？**

因为它们验证的是「我们拼的**字符串**与 `command.js` 一致」——而字符串**确实**
一致（`-O… -f…` 逐字对得上 `command.js:104`）。错的是**工具名**：把 `mfoc`
写成了 `nfc-mfclassic`。参数对、工具错，这类缺陷在「字符串对拍」的框架下
**原理上不可见**。

这也是 S11-6（数据流）、S11-7（假接线）之后的第三类：**验证的对象不是代码，
而是代码与外部世界的关系**。前两类靠通读代码能发现，这一类必须真跑。

**已加的两层防护：**

1. `crates/nfc-core/tests/real_tools.rs`（9 项）——工具在位、动态库解析
   （抓 rpath 没设，即 `compile.sh` 漏了 `patchelf` 那步）、门禁与 Busy 语义
2. `crates/nfc-core/tests/tool_cli.rs`（6 项）——把 engine 真正会 spawn 的
   每条命令行喂给真二进制，断言「它抱怨的是**预期**错误（没卡）」而非
   「退出 0」

两个文件在找不到 `framework/bin` 时整体跳过（CI 没编 C 工具是正常状态），
可用 `NFC_FRAMEWORK_BIN` 指定目录。已做变异验证：把读卡工具改回
`nfc-mfclassic`、破坏 rpath、删掉任一工具，三种情况都会红。

**顺带修正**：`KNOWN_TOOLS` 此前只有 8 个且不含 `mfoc`，注释里还写着一句
「本重写改用 `nfc-mfclassic`」——那句话本身就是这个 bug 的自白。现为 9 个。

### 6.18 S12-3：交叉编译出一个 `.exe`，顺手查出控制台黑框

Linux 上把 `x86_64-pc-windows-gnu` 目标装上 + mingw 工具链，就能真的编出
Windows 可执行文件（本机产出一个 13.2 MB 的 PE32+）。查 PE 头时发现：

```
Subsystem = 3   (3 = Console, 2 = GUI)
```

即双击会先闪一个黑框再开窗口。原版是 Tauri，默认就是 GUI 子系统，**没有
这个框**。这类问题在 Linux 上无论怎么测都看不到——只有真的产出目标平台的
二进制才现形。

修：给 `main.rs` 加

```rust
#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]
```

带 `not(debug_assertions)` 是因为 `--selftest` / `--version` 要往 stdout 写
结果；release 下 GUI 程序没有 stdout，勾上会让 CI 里看不到输出。debug 保留
console，release 用 GUI。

**这是一条只在交叉编译时才会暴露的缺陷**，故 CI 的 Windows job 现在会校验
PE 子系统（`Subsystem != 2` 即失败）。只靠「构建成功」是不够的——它确实成功
了，只是产出了一个带黑框的 GUI。

### 6.19 S12-5：把原版唯一的真实测试套件移植过来，抓出 2 个真缺陷 + 1 类假 fixture

前四个 bug（S11-6 数据流、S11-7 假接线、S12-2b 工具名错、S12-3 PE 子系统）
都是**自己写测试**发现的。但本项目从零重写，原作者踩过的坑我们凭什么重踩一遍？

原版仓库里有一个 `test/parse/keyParser.test.js`——**原项目唯一的可执行真相源**，
184 行、6 组断言，核心是**分块不变性**：stdout 一次喂进来的字节数与扇区边界无关，
解析结果必须与整块解析逐字节相同。

把 6 组断言**逐条、不改数字**移植到 `tests/orig_keyparser.rs`，立刻挂 2 组：

#### 缺陷 A：扇区号是「序号/2 反推」的，不是从输出读的

原版 `keyParser.js:20`：

```js
const head = sectorRe.exec(line)
if (head) sector = parseInt(head[1], 10)   // ← 从 "Sector NN - " 行头取
if (sector === null) continue             // ← 没有行头就整行跳过
```

本重写却是 `sector = self.index / 2`（`next_sector`）。**注释还写着**「扇区号沿用
原版的假设：每个扇区恰好两条，`sector = 序号 / 2`」——但原版根本没这个假设。

序号反推只在「每扇区恰好两条密钥、且工具不跳扇区」时才等于真实扇区号。一旦
工具跳过某个扇区（或某行只输出一条），序号就和真实扇区号分叉，**且静默错位**。
变异测试里回退到旧实现，断言立刻炸：

```
未知密钥未回填
  left:  [(0, A), (0, B)]     ← 实际算成了扇区 0
 right:  [(1, A), (1, B)]     ← 真实是扇区 1
```

用户在界面上看到的是「扇区 1 的密钥被记到了扇区 0」——**不报错，只是错**。

#### 缺陷 B：大写 hex 没归一化

原版 `keyParser.js:28` 有 `.toLowerCase()`。本重写漏了。而 `keys.txt` 里存的是
小写，于是「工具报出的大写密钥」与「文件里的小写密钥」**永远比不相等**，
合并去重失效，keys.txt 会越滚越大。

#### 更要命的发现：一整类 fixture 是**凭空编的**

改完上面两个，另有 11 个测试挂掉。查下去发现问题不在实现，在**测试数据本身**：

`tests/fixtures/mfdetect-keys.txt` 长得像这样：

```
MIFARE Classic 1K detected
 Found   Key A: ffffffffffff
 Found   Key B: ffffffffffff
 Found   Key A: ffffffffffff
 ...
```

**没有 `Sector` 行头**，而且每个「扇区」给了 3 条密钥。可真实工具
（`nfc-mfdetect.c:448-470`，`mfoc.c:447` 同款）打的是：

```c
fprintf(stdout, "Sector %02d - Found   Key A: %012llx ", i, ...);  // A、B 同一行
fprintf(stdout, "Found   Key B: %012llx\n", ...);                  // 或 Unknown Key B
```

即：**带行头、每扇区恰好 A/B 两条**。

这批 fixture 是**照着「看起来像」写的**，从没跟真二进制对过。它们的形状恰好
和「序号/2 反推」这个错误实现自洽——**错误实现 + 编造的 fixture = 一片绿**。
这正是 S12-2b 那一课的翻版：当验证数据和被验证代码来自同一个错误理解时，
测试只会把错误固定下来。

已按 `nfc-mfdetect.c` 的 `fprintf` 逐字重建 `mfdetect-keys.txt` / `mfoc-output.txt`，
并把 `engine.rs`、`detect.rs`、`integration.rs`、`selftest.rs` 里所有内联的
伪造行格式一并改真。

**教训**：fixture 必须从**真源码的 `fprintf`** 抄，不能照着「读起来像」编。原版
测试套件之所以珍贵，正是因为它的 `mfdetectOutput()` 明确注明了出处
（keyParser.test.js:20-21 指向 `nfc-mfdetect.c:451-468`）。

#### 已加的防护

- `tests/orig_keyparser.rs`：原版 6 组断言逐条移植，原版挂就是我们挂，不许改测试迁就实现
- 静态守卫改掉方向——原先断言 `self.index / 2` **存在**，把错实现当正确锁住；
  现在断言它**不得存在**，并要求行头正则、无行头跳过、小写归一化、原版套件已移植

### 6.20 S12-8：设备「已连接」的判定，两条通道被合成了一条

S12-5 之后继续核对 `nfc-list` 的连接判定，又抓到一个**用户完全看不见**的缺陷。

原版 `command.js:791-806` 把两个判定**分给两个回调**：

```js
exec(…, "nfc-list", [],
  (value) => {                                    // ← processHandler，只看 stdout
    if (value.indexOf("NFC device: NFC_Device opened") >= 0) { … connected = true }
  },
  settle,
  (value) => {                                    // ← stderrHandler，只看 stderr
    if (value.indexOf("Unable to open NFC device") >= 0) { … connected = false }
  })
```

为什么必须分开：libnfc 的错误走 `ERR()`，即 **stderr**
（`nfc-list.c:155` `ERR("Unable to open NFC device: %s", …)`），而成功标志
`NFC device: … opened` 走 **stdout**。两条回调**互不覆盖**，且 stderrHandler
在**进程退出时**才跑——它的作用正是把先前的 `true` 纠正回 `false`。

本重写把两个流混进同一个缓冲区、用一个 `judge_connect()` 判，且判到一次就
`connected.is_none()` 短路不再改。于是：

```
stdout: "NFC device: NFC_Device opened"      → connected = true（锁定）
stderr: "Unable to open NFC device"           → 被短路吃掉
最终：connected = true
```

**用户看到的**：设备已连接，一切正常。
**实际发生的**：pn532 打开成功但握手失败，卡根本读不出来，且**没有任何错误提示**。

这不是臆想的场景——USB 转串口设备掉线、驱动未就绪、权限不足，都会走
「打开成功 → 握手失败」这条路径。

修：两条通道各自独立判定、与到达顺序无关，只在结论变化时打一条日志。
新增回归测试用真实的 `Chunk::stderr_chunk` 复现该序列。

变异验证：把判定退回「判到一次就短路」，该测试立刻红
（`left: Some(true)` vs `right: Some(false)`）。

#### 顺带修掉一处脆弱门禁

`verify_parity.py` 里 `serial.rs 单测 = 16` 是写死的个数，每加一个用例就得手工
改一次——S12-8 加到 17 时立刻漂移。同类问题此前已在 i18n 上犯过一次
（`zh-CN.json 应为 158 key`）。改成下界断言 `>= 17`：只保证「够多」，不阻塞
正常新增。

**这类「把数量写死」的守卫都是自找的漂移源**：它们看起来在防退化，实际在逼你
维护一个与代码无关的数字。凡是「必须恰好 N 个」的门禁，都该问一句：真退化时
N 会变小吗？不会的话就不该写死。

### 6.21 S12-9：把 fixture 的出处**登记成制度**

S12-5 抓出「照着看起来像编的」fixture，S12-8 又在 `collect` / `nfc-list` 上续挖到
几处。逐个核对下来，编造串全都不是随手写的，而是**照着「读起来像」补的**：

| 编造的串 | 实际情况 | 出处 |
|---|---|---|
| `Reader #0: pn532 USB …` | nfc-list 从不打这一行 | `nfc-list.c:164-186` |
| `Trying 000000000000` | cropto1_bs 从不打 `Trying` | `hardnested_bruteforce.c:168` 只有 `Key found: %012llx` |
| `Unable to init device …` | libnfc 只有 `Unable to open NFC device` | `nfc-list.c:155` |
| `NFC reader(s) found:` | 同上，没有这一行 | 同上 |
| `\tcollecting nonces…`（制表符前缀） | 三个子串在**同一行**，无制表符 | `command.js:304-312` + `keyParser.test.js:162-164` |

都已按 C 源码逐字重建。**好消息**：重建后 473 个测试**全过**——说明解析器本身
一直是对的，错的只是喂给它的数据。

#### 但逐个核对救不了下一次

S12-5 我已经把 `mfdetect-keys.txt` / `mfoc-output.txt` 改真了，S12-9 又在另外
四个 fixture 里挖出同类问题。**问题在于**：新写 fixture 时没有任何机制提醒我
「这个串得先在 C 源码里找到出处」。

于是改成制度：

1. 新增 `tests/fixtures/README.md`——**出处登记表**。每个 fixture 登记抄自哪个
   C 文件的哪条 `printf`，并列出该格式的要点（哪几个子串同行、扇区号带在行头、
   走 stdout 还是 stderr）。
2. 静态守卫要求：每个 `.txt` 都必须出现在登记表里；且几个已确认的编造串
   （`Reader #` / `Trying 0` / 前置制表符）不得再出现。
3. 同一份 README 末尾附上**三条判定的通道归属表**——这是 S12-8 那个缺陷的
   根源，摆在 fixture 旁边比放在架构文档里更可能被看到。

新增 16 项静态守卫（共 685 项）。变异验证：把 `Reader #0:` 塞回 fixture → 红；
从 README 删掉一条登记 → 红。

**这条其实是 S12-5 的真正教训**：我当时的修复是「把编造的数据改成真的」，
但**没有回答「下次怎么保证不再编」**。把正确答案写进注释不够——需要让它
成为**不做就红**的门禁。


### 6.22 S13：设备枚举与连接握手——原来是「实现写好但没接线」

复查发现 `serial.rs` 的 `PortScanner` / `ConnectFlow` / `RealSerial` 早已实现并
带单测，但**生产代码 0 引用**：`nfc-app` 没启用 `real-serial` 特性，`Engine` 从不
调它们。于是发布版整条设备链路是死的：

- `Engine::scan()` 原本 spawn `nfc-list`，而原版是 `SerialPort.list()` 枚举串口；
  更糟的是 scan 不走 `launch`、`self.running` 恒为 `None`，输出只进日志，
  **`device_list` 永远为空**——设备下拉框永远没东西可选。
- `Engine::connect()` 只写 `libnfc.conf` 并置 `Connecting`，没有任何代码把它推进
  到 `Connected` / `Failed`。`device_state` 永久停在 `Connecting`，之后再点连接
  直接 `Busy`。**这是永久死锁。**
- `RealSerial` 因特性未启用从未被任何 build 编译过——`cargo metadata` 不做类型检查。

修法（本版）：

1. `Engine` 持有 `PortScanner`，`scan` 改为串口枚举并推 `Event::DeviceList`，
   **不占任务位、不过门禁**（对齐原版 `SerialPort.list()` 不经 `exec`）。
   同一枚举错误只报一次日志，避免 500ms 轮询刷屏。
2. `connect` 改为驱动 `ConnectFlow`：写配置 → `nfc-list` 握手 → 退出时落
   `Connected` / `Failed`（对标原版 `setNFCConfig` close 回调）。握手中置
   `is_running_task` 挡住并发任务。
3. `nfc-app` 启用 `real-serial`；`with_real_tools` 在该特性关闭时退回空列表。
4. 原版的「点开下拉才扫」改为**常驻 500ms 轮询**（S8 就有的刻意偏离，登记于
   §6.22）：支持热插拔。原版没有此轮询，只在 `index.html:14` 点开下拉时触发。

相关修复编号：S13 设备层接线（scan 枚举 / connect 握手 / 下拉 R5 从 `device_state`
派生，不再是不被写入的死字段）。

### 6.23 其他未做项的登记

- **`no_output_timeout`（无输出看门狗）本版本不做**：docs/01 §1.6 决策 #7 提过
  「默认关闭、硬破解任务可选配」，但原版 `execUtils.js` 也**没有任何超时机制**
  （工具挂死则任务一直挂着）。实现它会引入新的偏离且改动大，故登记为不做——
  行为与原版一致。若将来要做，别忘记它只能作用于前台硬破解任务，不能误伤
  `nfc-list` 这类长驻探活进程。
- **时间戳用 UTC 而非本地时区**（`paths.rs::timestamp`）：Rust 标准库无时区，
  影响仅文件名/日志名，已披露于 README。见 §6.22 附近说明。

### 6.24 S14 手机/手环操作区：与上游 Tauri 实现对齐的取舍

S14 新增 4 个 action（`open-phw-window` + 3 个 `phw-*`），行为**对齐上游 Tauri 端口**
（`3316b08` 首次实现、`f835e4e` 修块号校验），而非早期的 PN532CardReader 反编译方案。
三处关键取舍：

1. **读卡号读「当前卡」而非选 dump 文件**：`phw-read-uid` 走
   `nfc-mfdetect -O<temp.mfd> -f<keys>`（复用 `detect::detect_args(paths, true)`），
   成功后取 temp 前 16B 缓存 block0。放弃了旧方案「弹文件框选母卡 dump」——
   读当前卡更直接，且与上游一致（母卡需先解好，keys.txt 里已有密钥）。
2. **写 UID 位带 BCC 校验**：`phw-write-uid` 用 `block0_bcc_ok`（前 4 字节异或==第 5 字节）
   判断是否给 `nfc-mfsetuid` 追加 `-f` 强制写。这是上游新增的健壮性，比静默改写更可预期。
3. **写数据扇区限块 1-2、temp 自作 keys**：块 0 只读、块 3 是扇区尾块（密钥/ACL），
   故 `SectorBlock::is_valid` 只放行块 1-2；整卡写回用读回的 `temp.mfd` 自身当
   `nfc-mfclassic` 的 keys.mfd（前 4 字节 UID 匹配 + 密钥区即读回实际密钥），**不**自造
   全默认密钥文件。偏移公式 `(sector*4+block)*16` 与上游逐字一致。

**刻意偏离原版（Electron）**：原版 `command.js` 无 phw，这 4 项是 S14 增量；
对照源改用 `src-tauri/src/commands.rs`（原版 25 个新 commit 后才有的 Tauri 实现）。
未纳入本版的上游新能力（nonce 合并、全卡解密/mfcuk、手动 UID 输入、dump 导出密钥等）
登记在 verify_parity 的「上游独有 57 个 key」名单，属 v2 边界。

### 6.26 S17 写卡链路安全加固（刻意偏离原版）

S17 的出发点不是「对标原版」，而是「原版这几处会**写坏卡**或**误导用户**」。
逐条登记（均属刻意偏离，已同步 `tools/verify_parity.py` 的 `S17_EXTRA` 4 个
i18n key）：

| # | 偏离 | 原版 | 本项目 | 理由 |
|---|---|---|---|---|
| 1 | 写 UFUID 的 UID 位 | `nfc-mfsetuid -q <block0>`，BCC 不自洽时**追加 `-f` 强写** | 不追加 `-f`；`phw_write_uid` 在调用前判 `block0_bcc_ok`，不自洽直接拒绝并落日志 `log_msg_block0_bcc_invalid` | `nfc-mfsetuid` 自己都写「an invalid BCC can brick the card. Use -f to force」。自动追加 `-f` 等于替用户做不可逆的砖卡决定 |
| 2 | 手机/手环两个写按钮 | 无应用内确认窗，engine 的 `confirm_danger` 拿不到预置值一律返回 false，**点了没反应** | 补 `ConfirmKind::PhwWriteUid` / `PhwWriteData` 应用内确认窗（正文含缓存卡号与目标扇区块），确认后才派发 | 原本是接线漏了（§6.12 同类），但补确认窗才是正解——写卡号/写数据都是不可逆的 |
| 3 | 写卡/格式化成败判定 | 只看退出码 `code === 0`；`nfc-mfclassic` 大写 `A` 容忍失败仍退出 0，会把「部分块写入」误报成成功 | 新增 `BlockStatsParser` 解析 `Done, X of Y blocks written.`，完整判据 `written == total - 1`（`w`/`f` 不写 block0，Y 含 block0）；无完成行（工具中途失败）退回退出码 | 大写 `A` 下「60/64 块写入」退出码仍是 0，原行为等于骗用户「写好了」 |
| 4 | 失败后原卡备份 | 第二段 close 时**无条件 unlink** `temp.mfd` | 成功且完整才删；部分写入 / 工具失败 / 被 kill 都**保留** temp 并落日志 `log_msg_backup_kept` + 完整路径 | 写卡一旦部分成功又报错，用户就失去了唯一能恢复原卡的东西。保留备份的代价只是多占一个 1–4KB 文件 |
| 5 | 格式化卡片 | 无确认框（`command.js:144-149` 直接开跑），误点即清空 | 补 `ConfirmKind::FormatCard` 应用内确认 + engine 侧 `prepare_format` 的 `confirm_danger` 第二道闸；同时 `report:false` → `true`，纳入完成行判定 | 格式化是不可逆的清空操作，且原版「两道闸」的声明（README）对 format 本来就不成立 |
| 6 | `nfc-mflock` 结果 | 每一步 `transmit_*` 的返回值都被忽略，最后无条件 `exit(EXIT_SUCCESS)` | 解锁 ①②、写配置命令、写配置数据四步任一无回应即 `exit(EXIT_FAILURE)`；全成功才打印 `Card locked successfully` 并 exit 0 | 非 UFUID 卡、已封卡、或配置写入被忽略时，原版都显示「完成」，用户误以为锁卡成功 |
| 7 | 备份完整性 | `nfc-mfdetect` 只校验「全部扇区密钥找到」，不校验「每个块都读成功」；读失败的块在 dump 里是全 0，trailer 的 ACL 也可能为 0 | 新增 `-S` 严格模式（`detect_args(..., true)` 时写卡/格式化/手机写数据三处启用，`phw-read-uid` 保持宽松）；落盘前任一块读失败就不写 dump、非 0 退出 | 手机/手环「写数据扇区」会把整个 temp 写回当来源，缺块的备份会把不可读的块覆盖成 0（§6.12 同类的数据损坏） |

**不变的部分**：`w`/`f` 仍不写 block0（`nfc-mfclassic.c:419`）；备份闸仍要求
`temp.mfd` 存在且非空才启动第二段；`nfc-mflock` 的 `E1 00 + 85...08` 仍是
UFUID 封卡配置写入（经 Proxmark3 `doc/magic_cards_notes.md` 的 UFUID 封卡序列
`40 / 43 / e100 / 85000000000000000000000000000008` 逐字核对），不改 UID。
