# 06 · 界面改版实施方案（三栏工作台）

> 状态：**待实施**。设计方向已与项目所有者确认（2026-11）。
> 交互原型：[`docs/design/ui-redesign-proposal-v2.html`](design/ui-redesign-proposal-v2.html)（单文件、无依赖、含模拟数据交互，浏览器直接打开；v2 = 修正扇区 ACL 列取值并强化权限解读）。
> 本文是该原型的 Rust（egui/eframe）落地规格与实施计划。行为对齐约束（39 个 action、门禁、危险确认、i18n）均不变。

---

## 1. 背景与问题

现版主窗口（`crates/nfc-app/src/app.rs::draw`，自上而下）：标题栏 → 引导条 → 三列按钮区 → 底部控制台。产品视角的已确认问题：

| # | 问题 | 现状代码位置 |
|---|------|--------------|
| 1 | 缺少"当前卡片"主角：UID/卡型/密钥状态只能翻日志或开子面板看 | `app.rs` 无卡片常驻区 |
| 2 | 三列按钮并排无流程感，且写卡列 8 个按钮把整行撑高，列间留白失衡 | `app.rs::button_area`（约 L1893） |
| 3 | 控制台常驻底部挤压操作区，宽屏利用率低 | `app.rs::console`（约 L2167） |
| 4 | 危险操作（格式化/锁 UFUID）与普通按钮混排，警示不足 | `app.rs::button_area` 的 `BtnStyle::Danger` |
| 5 | 解卡结果（扇区数据、密钥分布）不可视，用户对"破解进度"无感知 | 无对应 UI |

## 2. 已确认的设计决策

| 决策点 | 结论 |
|--------|------|
| 布局 | **三栏工作台**：左=操作按钮组，中=当前卡片 + 卡片扇区编辑器，右=状态栏（设备/任务/事件/控制台） |
| 卡片上下文 | 要。解卡结果常驻中栏顶部，替代"转储已保存"临时引导条的入口职能 |
| 危险操作 | 红色描边 + 警示图标，与普通按钮明确区分；确认弹窗机制不变 |
| 视觉主题 | 沿用现有品牌蓝与 `theme.rs` 全部 token，不换色 |
| ACL 解读 | 要。扇区编辑器展开扇区时显示访问控制位的人话解读，算法与 `nfc-core::dumpcheck` 同源 |
| 步骤感 | 左栏分组标题带编号（1 读卡 / 2 破解 / 3 写卡 / ＋ 更多）与状态点（待命/运行中/完成） |

## 5. 组件规格

### 5.1 左栏 ops_panel

- 四个分组：`读卡`（一键解卡=primary、已知密钥解卡、检测卡片加密=ghost）、`破解密钥`（HardNested、字典测试）、`写卡`（一键写卡=primary、格式化=danger）、`更多操作`（手机/手环、CUID 写、写入卡号(手动)、写入 UID(从文件)、全加密爆破、锁定 UFUID=danger）。
- 分组标题：编号徽标（1/2/3/＋）+ 组名 + 状态点：
  - `运行中`：该组内任一 action 处于 `state.is_running_task` 且任务名匹配；
  - `完成`：读卡组=存在本次会话转储；破解组=`unknown_key_info.is_empty()` 且执行过检测；写卡组=本次会话写卡成功事件。
  - 状态仅作视觉提示，**不参与门禁**。
- 按钮尺寸：主按钮高 38、普通 32；危险按钮红描边（`danger_strong` 描边 + `danger` 图标色，悬停填充 `danger` 10% 透明度）。
- 门禁：沿用 `nfc_core::command::spec(action)` + `command::gate(s, &self.state)`，禁用时 `on_disabled_hover_text(reason)`，与现版逐字一致。

### 5.2 中栏 · 当前卡片（card_context）

| 字段 | 数据来源 |
|------|----------|
| UID（紫色高亮 `theme.uid`） | 卡片快照：解卡/读卡完成后从 dump 头 16 字节解析（块 0 前 4 字节 + BCC 校验，复用 `dumpcheck::bcc_expected` 语义） |
| 卡型 | dump 字节数 → 1K(1024B)/4K(4096B) → "MIFARE Classic 1K/4K"（容量判定复用 `dumpcheck::sector_count` 语义） |
| 密钥统计条 | `state.known_key_info.len()` / `state.unknown_key_info.len()`，绿/琥珀比例条 |
| 转储文件名 + 时间 | `DumpSaved` 事件携带的路径（现有 `guidance_dump_saved` 文案的来源） |
| 操作 | 「写这张卡」= 现 `DumpSaved` 引导条按钮的常驻化（仍走 `write-IC` + 确认框）；「编辑转储」打开现有 `open-dump-editor` 面板 |
| 空态 | 虚线框 + "尚未读取卡片…点击左侧「一键解卡」" |

`DumpSaved` 引导条保留（写这张卡 / 打开转储目录），并在卡片档案条上叠加常驻「写这张卡」按钮（同参同链路）；其余引导场景（冷启动连接、未知密钥引导、缺失工具）不变。

### 5.3 中栏 · 卡片扇区编辑器（sector_editor）

- **数据源**：卡片快照的 dump 字节 → `nfc_core::model::dump::to_sector_lines` 得到逐扇区 4 行 hex（与转储编辑器同一解析）。解卡任务成功回调里加载一次并存入 `NfcApp.card_snapshot`，**不每帧读盘**。
- **行渲染**：每扇区一行（等宽字体）：扇区号(2 位) | KeyA | ACL(3 字节) | KeyB | 状态标签。KeyA/KeyB 着色：已知=绿（`STATUS_OK`）、未知=琥珀（`STATUS_WARN`）并显示 `?? …` 占位（密钥明文仅在 `known_key_info` 命中时显示）。
- **展开交互**：点击行展开该扇区 4 块 hex（`open_sector: Option<usize>`，同时只展开一个）。默认解卡后展开扇区 0（可直接看到 UID 块）。
- **容量自适应**：1K=16 扇区（尾块=首块+3）；4K=40 扇区，32 号起 16 块/扇区（尾块=首块+15）——与 `dumpcheck::sector_first_block / sector_trailer_block` 语义一致。
- **ACL 解读**（见 §6）随展开内容显示在块数据下方。
- 性能：`ScrollArea::show_rows` 按行虚拟化（40 扇区 × (1 行 + 展开详情) 量级很小，常规 `ScrollArea` 亦可）。

### 5.4 ACL 解读规格

算法**逐行移植** `dumpcheck.rs`（原版 `dumpTools.js` ReadAC/ReadRAC），输入尾块字节 6..10：

```
forward[i] 与 reversed[i]（公式见 dumpcheck.rs L61-L79，此处不重复）
```

- 对每块 i∈0..4：`forward[i] != reversed[i]` → **ACL 已损坏（AclCorrupt）**，显示红色告警行 + 提示可到转储编辑器修复（现有 `fix` 能力）；这是与仓库体检/修复行为同一套判定。
- 一致时得到每块 C 值（0..=7），查表显示权限：

| C | 数据块 0-2 | 尾块 3 |
|---|-----------|--------|
| 0 | 读 A\|B · 写 A\|B | KeyA 不可读·可写(A)｜ACL 读(A)｜KeyB 读写(A) |
| 1 | 读 A\|B · 写 ✕ | KeyA 不可读写｜ACL 读(A)｜KeyB 读(A) |
| 2 | 读 A\|B · 写 ✕ · 减值 A\|B | KeyA 不可读写｜ACL 读写(A)｜KeyB 不可读写 |
| 3 | 读 B · 写 B | KeyA 不可读写｜ACL 读(B)｜KeyB 不可读写 |
| 4 | 读 A\|B · 写 B | KeyA 不可读·可写(B)｜ACL 读(B)｜KeyB 不可读·可写(B) |
| 5 | 读 A\|B · 写 ✕ | KeyA 不可读·可写(B)｜ACL 读写(B)｜KeyB 不可读写 |
| 6 | 读 A\|B · 写 ✕ | KeyA 不可读写｜ACL 读写(B)｜KeyB 不可读写 |
| 7 | 全部禁止 | 全部禁止 |

- 表值以 NxP MF1S50 datasheet 为准，实施时以单测钉住常用值：`FF 07 80 69 → C=[0,0,0,1]`、`08 77 8F xx → C=[6,6,6,3]`（两例均已被 `dumpcheck` 测试或原型验证）。
- 价值联动：写卡前用户可直观看到"哪些扇区只读"；对应真机验收项「有 ACL 保护块的卡写数据扇区应中止」。

### 5.5 右栏 rail

| 卡片 | 内容 | 迁移来源 |
|------|------|----------|
| 设备 | 状态点 + 文案 + 设备名 + 刷新按钮（`scan-usb-devices`） | 原 `device_status_chip` 信息 + 标题栏下拉并存（原型如此，实施时保留两处入口） |

## 6. 状态与数据流

`NfcApp` 新增字段（全部 UI 态，不进 `nfc-core::state::AppState`）：

```rust
pub struct CardSnapshot {          // 解卡/读卡成功后构建一次
    pub uid: String,               // 8 位 hex
    pub card_type: &'static str,   // "MIFARE Classic 1K" / "4K"
    pub sectors: Vec<Vec<String>>, // to_sector_lines 的编辑器形态
    pub file: PathBuf,             // DumpSaved 路径
    pub time: String,
}
pub card_snapshot: Option<CardSnapshot>,
pub open_sector: Option<usize>,    // 扇区编辑器展开行
```

- 事件流不变：`Engine` → `state.apply(Event)` → UI 每帧读 `state`。任务成功回调（`consume_pending`/任务完成处）在 `DumpSaved` 后构建快照。
- 计时器、热插拔轮询、`logic`/`ui` 顺序等既有机制**不动**。
- 不引入任何新线程、通道、网络（外联审计红线）。

## 10. 风险与缓解

| 风险 | 缓解 |
|------|------|
| 窄窗口三栏挤压 | 断点回落 + `CONSOLE_RESERVE_H` 思路沿用：中栏 `ScrollArea` 设 `min_height`，任务卡始终完整可见 |
| 每帧重绘扇区表卡顿 | 快照只在任务成功时构建一次；渲染走 `ScrollArea::show_rows`；hex 文本零拷贝引用 `String` 切片 |
| selftest 断言脆弱（结构大改） | P0 先只动骨架并修断言，再逐阶段迁移，保持每步全绿 |
| ACL 权限文案与 datasheet 有出入 | 表格集中在一个 `const`，单测钉住解码值；文案可独立修订 |
| 4K 卡未实测（CI 无硬件） | 容量逻辑复用 `dumpcheck` 既有判定并有单测；真机项列入 §9 清单 |
